# 青泉谷 P1：OrderAI → 雲鼎 ERP 隔離驗收

## 適用範圍

本驗收只驗證青泉谷 P1 的受控資料路徑：**LINE／內部轉交素材所形成的 OrderAI 草稿，經買方文字確認與人工覆核後，送入雲鼎 ERP 的「待確認客戶」及「待確認訂單」**。驗收使用短生命週期的 SQLite、localhost、合成租戶、合成商品、合成庫存與測試金鑰；不使用 LINE 官方帳號、雲鼎正式端點、正式資料庫、真實憑證或真實客戶資料。

> 這不是正式上線驗收，也不是對外營運測試。測試完成後，暫存 ERP 程序與資料庫會被停止及清除。

## 受控流程

| 階段 | 必要條件 | 系統動作 | 禁止動作 |
|---|---|---|---|
| 草稿建立 | 已通過既有解析與商品映射閘門 | 建立受控案例與被封鎖的 outbox | 建立本地正式客戶或訂單 |
| 人工覆核 | 人員確認買方已文字確認「誰、要什麼、數量、何時要、特別要求」 | outbox 由 `blocked` 改為 `queued` | 自動送件、直接確認、承諾庫存 |
| 隔離送件 | `P1_ISOLATED_DELIVERY_ENABLED=true`，目標只能是 localhost allowlist | 依實際 HMAC／timestamp／nonce 呼叫 ERP service ingress | 對外網路、正式 ERP、付款、預留、扣庫、出貨、開票 |
| ERP 暫存 | HMAC 驗證、nonce 未重複、公司範圍一致 | 建立待確認客戶與待確認訂單 | 建立正式 Customer 或 Order |
| 結束 | 成功送件 | OrderAI case `closed`、outbox `delivered` | 重複送件或自動人工確認 |

## 需驗證的結果

隔離驗收測試 `tests/test_p1_cross_module_isolated_acceptance.py` 會在不同 Python 程序啟動暫存 ERP，避免兩個儲存庫皆使用 `app` 套件名稱所造成的匯入混用。測試必須證明以下事實。

| 驗收項目 | 必須結果 |
|---|---|
| HTTP 簽章 | ERP 接受兩次獨立 HMAC／nonce service ingress；收據為 2 筆且 nonce 雜湊各不相同 |
| 待確認客戶 | 僅 1 筆，顯示名稱以密文保存，未連結正式 Customer |
| 待確認訂單 | 僅 1 筆，連結上述待確認客戶，`formal_order_id` 為空 |
| 正式資料 | ERP 正式 Customer 與正式 Order 均為 0 筆；OrderAI 本地正式 Customer 與 Order 亦均為 0 筆 |
| 庫存與交易 | `reserved=0`；無付款、扣庫、出貨、開票行為 |
| OrderAI 狀態 | case 為 `closed`；outbox 為 `delivered`、`attempt_count=1` |
| 稽核與重送 | 稽核不含草稿明文或電話；第二次送件被狀態閘門拒絕，ERP 資料計數不變 |

## 預設安全配置

`P1_ISOLATED_DELIVERY_ENABLED` 預設為 `false`。即使已安裝 ERP HTTP adapter，只要隔離開關未開、目標 URL 無效或主機不在 `P1_ERP_ISOLATED_ALLOWED_HOSTS` 中，送件都必須 fail-closed。生產設定不得把本驗收所用的合成密鑰、SQLite 路徑或 localhost 測試值帶入。

## 正式試行前的獨立門檻

1. OrderAI PR #27 與雲鼎 ERP PR #20 必須經獨立程式碼審查並由具權限人員合併。
2. 需另行取得正式環境、正式憑證、資料保護與測試範圍的書面授權；本驗收不構成該授權。
3. 必須另行核實 LINE 官方帳號 webhook 設定、真實簽章驗證、服務帳號、ERP endpoint、資料保留與稽核政策。
4. 正式試行仍須維持人工客戶確認、人工 ERP 確認與所有 fail-closed 規則；不得因隔離驗收成功而放寬此邊界。
